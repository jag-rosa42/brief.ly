       │               │                │

                            │
                            ▼
                      Personalization
```

 Traefik is designed around routers, services and middleware, so this is exactly the sort of edge routing it can handle.  Traefik Docs+1

 # 3\. How does authentication work?

 This is where Traefik's **ForwardAuth** middleware becomes interesting.

 Traefik has a `forwardAuth` middleware that delegates authentication to an external HTTP service:

```
Request
   │
   ▼
Traefik
   │
   │ "Is this request authenticated?"
   ▼
Identity / auth verification endpoint
   │
   ├── 2xx → allow
   │
   └── 401/403 → reject
```

 That's an explicit Traefik feature. If the authentication service returns 2xx, Traefik forwards the original request; otherwise Traefik returns the authentication service's response.  Traefik Docs

 So you can reuse your **existing Identity service** instead of creating another authentication service.

 # 4\. Add one endpoint to Identity

 For example:

```
GET /auth/verify
```

 or:

```
GET /auth/introspect
```

 I prefer something like:

```
GET /auth/verify
```

 Its job is **not** to return an account.

 Its job is simply:

 > "Is this access token valid?"

 The request from Traefik would contain:

```
Authorization: Bearer eyJ...
```

 Identity validates:

```
Bearer token
     │
     ▼
JWT signature
     │
     ▼
algorithm
     │
     ▼
expiration
     │
     ▼
token type = access
     │
     ▼
claims
     │
     ▼
VALID
```

 Then:

```
HTTP/1.1 204 No Content
```

 or `200 OK`.

 If invalid:

```
HTTP/1.1 401 Unauthorized
```

 # 10\. One complication: you're using Podman

 This is where I would **not blindly copy a Docker + Traefik tutorial**.

 Traefik's official container integration documentation focuses on its Docker provider, which discovers containers through the Docker API and labels.  Traefik Docs

 Podman does provide a Docker-compatible API layer, so there are ways of making Docker-oriented tooling interact with Podman. Podman's API documentation explicitly describes a Docker-compatible API, and the Podman service can expose that API through its Unix socket.  Podman Documentation+1

 But I don't think we need to make your architecture depend on that.

 For your project, I would seriously consider using **Traefik's file provider** instead.

 Traefik supports a file provider where routers, services and middleware can be explicitly declared in YAML/TOML.  Traefik Docs

 That gives you:

   │

   ├── identity

   └── ai-processing

 and Traefik simply knows:

```

 No need for Traefik to control or inspect Podman.

 I think that's particularly attractive for your project.

 # 15\. Where should the `Authorization` header go?

 With the ForwardAuth architecture, there are two choices.

 ### Choice A — Gateway consumes it

```
Browser
  │
  │ Authorization
  ▼
Traefik
  │
  ▼
Identity /verify
  │
  ▼
Personalization
```

 Traefik validates it and doesn't forward it.

 ### Choice B — Gateway validates it and forwards it

```
Browser
  │
  │ Authorization
  ▼
Traefik
  │
  ├── verify with Identity
  │
  ▼
Personalization
  │
  └── Authorization still available
```

 For your architecture, **I would initially use B**.

 Why?

 Because it gives your services the option to perform additional authorization based on the original JWT without requiring the frontend to change.

 But there's an important security consideration:

 > If the gateway is the only component responsible for authentication, the backend services must be inaccessible except through the trusted gateway.

 Otherwise someone could bypass Traefik and directly call:

```
http://personalization:8000
```

 That's why removing the published backend ports is important.

 # 16\. What does Identity return to Traefik?

 This is another interesting possibility.

 Identity could return:

```
HTTP/1.1 204 No Content

X-User-ID: 2d8...
```

 Traefik can copy selected response headers from the authentication service to the forwarded request using `authResponseHeaders`. That's supported by ForwardAuth.  Traefik Docs

 Then:

```
Traefik
   │
   │ X-User-ID: abc
   ▼
Personalization
```

 But **don't blindly trust arbitrary incoming `X-User-ID` headers**.

 The gateway needs to overwrite/remove the client-provided version before adding its own.

 And I'd probably not introduce this immediately.

 You already have:

```
sub = account_id
```

 in your JWT.

 So we should first decide whether downstream services need the user ID from:

```
Authorization JWT
```

 or:

```
X-User-ID
```

 There are tradeoffs.

 # 17\. One concern with your current Identity service

 There is one architectural change I would make before building the gateway.

 Currently:

```
JWTTokenService
```

 has:

```
self._public_key = settings.JWT_PUBLIC_KEY
```

 and Identity has both:

```
jwt_private_key
jwt_public_key
```

 which is fine.

 But now Personalization/Traefik needs the public key too.

 I don't want you to do:

```
shared/secrets/jwt_public_key
             │
             ├── Identity
             ├── Personalization
             ├── Content
             ├── Traefik
             └── ...
```

 forever.

 The better long-term model is:

```
Identity
   │
   │ publishes
   ▼
JWKS
   │
   ├── Traefik
   └── other consumers
```

 Traefik's current JWT middleware in its Hub product supports JWKS URLs, but that particular JWT middleware is a **Traefik Hub feature**, not something I would assume is available in the open-source Traefik you're deploying.  Traefik Docs+1

 For open-source Traefik, `ForwardAuth` is therefore the more relevant mechanism for the architecture we're discussing.  Traefik Docs
