 # One important observation

 Your JWT currently contains:

```
{
    "jti": "...",
    "sub": "...",
    "type": "access",
    "iat": "...",
    "exp": "..."
}
```

 That's a good minimal foundation.

 However, when we move JWT verification to **Personalization, Content, Morning Briefing, etc.**, we'll need to decide whether claims such as:

```
iss
aud
```

 should be introduced.

 PyJWT supports validating both issuer and audience, and its documentation describes `aud` as identifying the intended recipients of a JWT.  PyJWT

 That's particularly relevant once you have multiple services.

 For example, we might eventually have:

```
Identity
   │
   │ signs
   ▼
JWT
   │
   ├── Personalization
   ├── Content
   ├── Morning Briefing
   └── ...
```

 At that point, we need to explicitly answer:

 > "Who is allowed to accept this token?"

 rather than merely:

 > "Is this token correctly signed?"

 Your current code already correctly restricts the algorithm with:

```
algorithms=[self._algorithm]
```

 which is important. PyJWT explicitly recommends that the allowed algorithm not be derived from attacker-controlled token data.  PyJWT

 # Another important point: your refresh-token design

 Your refresh-token architecture is actually more sophisticated than a simple stateless JWT implementation.

 You have:

```
Refresh JWT
     │
     ├── jti
     ├── sub
     ├── type=refresh
     └── exp
```

 and then:

```
jti
 │
 ▼
RefreshToken DB
 │
 ├── token_hash
 ├── account_id
 ├── expires_at
 ├── revoked
 └── replaced_by
```

 So you have **refresh-token rotation and revocation tracking**.

 This means that although the refresh token is a JWT, you are deliberately treating it as a stateful session credential.

 That's a useful distinction to preserve.

 Your access token is essentially:

```
short-lived
signed
stateless
```

 while your refresh token is:

```
signed
longer-lived
stored/revocable
rotated
hashed in DB
```

 That is a very different role.

 You have:

```
"jti": str(token_id),  # subject

 The comments are incorrect.

 They don't affect the implementation, but I'd change them because:

```
jti = JWT ID
sub = Subject
```

 So:

```
"jti": str(token_id),       # JWT ID
"sub": str(account_id),     # Subject / account ID
```

 Your Pydantic model reflects the correct meaning:

```
token_id: str = Field(alias="jti")
subject: str = Field(alias="sub")

 # The bigger architectural question starts here

 Your current:

```
GetCurrentAccount
```

 does this:

```
JWT
 │
 ▼
verify JWT
 │
 ▼
account_id
 │
 ▼
AccountRepository
 │
 ▼
Account
```

 That's completely reasonable **inside Identity**.

 But suppose Personalization receives:

```
GET /preferences
Authorization: Bearer eyJ...
```

 What should happen?

 There are now two fundamentally different possibilities:

 ### Option A

 Personalization verifies the JWT itself:

```
Personalization
   │
   ├── extract bearer
   ├── verify RS256
   ├── validate claims
   ├── extract sub
   └── use sub as account_id
```

 ### Option B

 Something in front of Personalization verifies the JWT:

```
Gateway
   │
   ├── verify JWT
   ├── identify user
   └── forward request
             │
             ▼
      Personalization
```

 And this is the **core architectural decision we need to solve next**.

 It also determines whether you need an API Gateway, what the gateway should do, and how much authentication code should live in your shared Python packages.

 ## There is also a subtle issue with your current `GetCurrentAccount`

 In Identity, you're doing:

```
account = self._accounts.find_by_id(claims.account_id)

if account is None:
    raise InvalidTokenError()
```

 That's appropriate if the question is:

 > "Does this authenticated token correspond to an existing Identity account?"

 But Personalization shouldn't necessarily need to call Identity every time:

```
Personalization
      │
      │ "Who is user X?"
      ▼
Identity
      │
      ▼
Identity DB
```

 That would create unnecessary coupling.

 Instead, one possible architecture is that Personalization trusts the cryptographic identity represented by the JWT:

```
JWT
 │
 └── sub = account UUID
          │
          ▼
   Personalization DB
```

 But whether that's appropriate depends on what your system considers authoritative and how account deletion/deactivation should propagate.

 That's one of the questions I'd like to settle rather than assume.
