 ### One important point already

 Your assumption that:

 > frontend gets tokens → sends token to API → backend services authenticate the token

 is broadly correct.

 But I would **not** automatically make every microservice responsible for implementing the entire authentication flow.

 A more maintainable architecture is usually:

```
Browser
   │
   │ HTTPS
   ▼
┌──────────────────────┐
│ Reverse Proxy /      │
│ API Gateway          │
│                      │
│ TLS termination      │
│ Routing              │
│ Authentication       │
│ Rate limiting        │
└──────────┬───────────┘
           │
           │
     ┌─────┴───────────────┐
     │                     │
     ▼                     ▼
Identity              Application
Service               Services
                         │
              ┌──────────┼──────────┐
              ▼          ▼          ▼
       Personalization   AI    Morning Briefing
```

 And there is an important nuance: **authentication at the gateway doesn't necessarily mean the downstream services should blindly trust the gateway**. Depending on your threat model, they may still validate JWTs themselves, or you can use signed/internal identity headers, mTLS, service identities, etc.

 Also, I would challenge one part of your assumption:

 > "all the connection between services can remain in HTTP"

 That can be acceptable **inside a properly isolated private network in some deployments**, but I wouldn't make it an architectural rule. If your services contain personal data or AI/user information, encrypting service-to-service traffic with TLS is often worth considering, particularly once the system is distributed across hosts or Kubernetes nodes.
